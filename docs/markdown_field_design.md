# Markdown Field Design For PollyDB

This document defines a concrete design for adding native Markdown field support to `pollydb` using the AST and chunk-planning facilities from [`vmarkdown`](/Users/guweigang/Source/vmarkdown).

The goal is not to store Markdown as one large row payload. Instead, a Markdown column should behave like a typed reference to an external AST-backed document store with structural sharing, semantic diffs, and merge-aware identity.

## Goals

- Keep typed table rows small and deterministic.
- Reuse unchanged Markdown blocks across versions and across documents.
- Preserve stable identity under reordering when content is unchanged.
- Avoid full-row rewrites for small edits to large Markdown documents.
- Support future semantic diff and merge at block granularity.
- Leave room for block-level derived indexes.

## Non-Goals For Phase 1

- Full inline-span indexing.
- Full-text search.
- Lossless preservation of parser extensions not present in `vmarkdown` yet.
- SQL grammar changes in the first implementation step.

## Why A Native Type

Current typed storage encodes column payloads inline in the row value. This works well for scalar and modest semi-structured values, but it is the wrong fit for large Markdown documents.

If a `100 KB` Markdown document is stored as a `string` or `bytes` column, a one-byte edit causes:

- a new row payload
- a new table leaf value
- a new hash chain to the table root

That defeats the structural-sharing benefits PollyDB is designed to preserve.

## Proposed Public Shape

Add a new typed column:

```v
pub enum ColumnType {
	bool_
	i64_
	string_
	bytes_
	enum_
	json_
	datetime_
	markdown_
}
```

`markdown_` is stored in the row as a compact descriptor, not as the full source text.

## Row-Level Value Contract

The row payload for a `markdown_` column is a serialized `MarkdownRef`.

```v
pub struct MarkdownRef {
pub:
	version        u8
	doc_root_id    string
	source_hash    string
	source_len     i64
	ast_version    u8
	parse_flags    u32
}
```

Meaning:

- `version`: storage contract version for the ref encoding.
- `doc_root_id`: root content ID for the Markdown document tree.
- `source_hash`: hash of the original source text after newline normalization.
- `source_len`: original source byte length.
- `ast_version`: version of the AST encoding contract used to compute IDs.
- `parse_flags`: parser options that affect structure.

Phase 1 read/write helpers should treat `markdown_` as an opaque typed payload outside the typed row codec.

## Internal Storage Model

One Markdown field expands into three internal layers.

### 1. Content Chunks

Deduplicated AST block payloads.

```v
struct MarkdownChunk {
	id   string
	kind string
	data []u8
	refs []string
}
```

This maps directly to the chunk representation already exposed by `vmarkdown`.

Responsibilities:

- cross-document deduplication
- cross-version reuse
- immutable block storage

### 2. Document Root

One logical Markdown document root.

```v
struct MarkdownDocRoot {
	id          string
	root_refs   []string
	source_hash string
	source_len  i64
	ast_version u8
	parse_flags u32
}
```

Responsibilities:

- identify one parsed Markdown document version
- point to top-level block content IDs
- bind source-level metadata to the root

### 3. Occurrence Manifest

Per-document node identities that distinguish repeated equal-content blocks.

```v
struct MarkdownOccurrence {
	occurrence_id string
	content_id    string
	parent_id     string
	kind          string
	anchor        string
	order         int
	path_hint     string
}
```

Responsibilities:

- document-local uniqueness
- semantic merge targeting
- move detection
- stable block-level diff output

## Two-Layer Identity Model

`vmarkdown` already gives a stable content-oriented ID through `stable_id()`. That is the right building block, but it is not enough by itself because identical repeated paragraphs inside one document would receive the same ID.

PollyDB should therefore use two identities:

### `content_id`

Directly reuse `vmarkdown.BlockNode.stable_id()`.

Properties:

- same content => same ID
- ideal for physical deduplication
- unchanged by relocation
- not unique for repeated equal siblings

### `occurrence_id`

Generated by PollyDB per document occurrence.

Suggested formula:

```text
occurrence_id = hash(
  parent_occurrence_id +
  "|" +
  content_id +
  "|" +
  sibling_duplicate_ordinal +
  "|" +
  semantic_anchor
)
```

Where:

- `parent_occurrence_id`: enclosing block occurrence or document root marker
- `sibling_duplicate_ordinal`: count of prior siblings with the same `content_id` under the same parent
- `semantic_anchor`: nearest heading chain, or parent anchor if no heading exists

This preserves identity better than raw positional indexes while still disambiguating duplicates.

## Anchor Rules

Anchor generation should be deterministic and cheap.

Recommended rules:

- heading blocks create a new anchor segment
- nested content inherits the nearest heading chain
- blockquotes and list items append local structural markers
- if no heading exists, anchor falls back to `/`

Examples:

```text
/
/h1:intro
/h1:intro/h2:design
/h1:intro/h2:design/list[0]
```

Anchor text should use normalized heading text with truncation and a short hash suffix when needed.

## Ingest Pipeline

Phase 1 should add a dedicated Markdown ingest path instead of routing through normal `TypedValueEncoder.encode_value`.

```v
pub fn ingest_markdown(raw string, options vmarkdown.ParseOptions) !MarkdownIngestPlan
```

Suggested plan shape:

```v
pub struct MarkdownIngestPlan {
pub:
	ref         MarkdownRef
	doc         MarkdownDocRoot
	to_add      []MarkdownChunk
	to_reuse    []MarkdownChunk
	manifest    []MarkdownOccurrence
	diff        []MarkdownDiffEntry
}
```

Ingest steps:

1. Normalize source newlines.
2. Parse with `vmarkdown.parse_with_options(...)`.
3. Collect block chunks using `stable_id()` and `binary_encode()`.
4. Build the document root.
5. Build the occurrence manifest.
6. Compare against the previous manifest if one exists.
7. Persist only missing chunks.
8. Store the new root and set the row value to `MarkdownRef`.

## Persistence Layout

There are two viable layouts.

### Option A: Dedicated internal tables

- `__md_docs`
- `__md_occurrences`
- `__md_chunks`

Pros:

- easy inspection and debugging
- natural fit for future block-level querying

Cons:

- more catalog surface
- more typed-table maintenance

### Option B: Virtual-root side store

- keep Markdown chunks outside normal typed tables
- bind document roots through repository virtual roots

Pros:

- cleaner separation from user tables
- smaller user-visible catalog

Cons:

- more custom plumbing
- querying needs an extra projection layer

Recommendation:

- Phase 1: use a dedicated internal side store, not user-visible typed tables
- Phase 2: optionally project block metadata into typed internal tables for indexing

## Typed API Additions

Recommended helper surface:

```v
pub fn (mut db PersistentDatabase) put_markdown(
	table_name string,
	primary_key []u8,
	column_name string,
	raw string,
) !MarkdownRef

pub fn (db &PersistentDatabase) get_markdown(
	table_name string,
	primary_key []u8,
	column_name string,
) !string

pub fn (db &PersistentDatabase) get_markdown_ref(
	table_name string,
	primary_key []u8,
	column_name string,
) !MarkdownRef

pub fn (db &PersistentDatabase) diff_markdown_refs(
	left MarkdownRef,
	right MarkdownRef,
) !MarkdownDiff
```

The typed row API should still allow direct `set(column, MarkdownRef)` in later phases, but Phase 1 should prefer explicit helpers so the write path can atomically persist side structures before mutating the row.

## Merge Contract

Raw typed merge treats each row value as an indivisible byte payload. For `markdown_`, that would create false conflicts and throw away semantic structure.

Markdown-aware merge should compare document manifests instead.

### Fast Cases

- same `doc_root_id` on both sides: unchanged
- only ours differs from base: take ours
- only theirs differs from base: take theirs

### Structural Auto-Merge Cases

- changes target different `occurrence_id` values: merge automatically
- one side moves a block, the other edits a different block: merge automatically
- one side edits content while the other only reorders equal-content siblings: merge automatically if occurrence mapping stays unique

### Conflict Cases

- both sides change the same `occurrence_id` to different `content_id` values
- both sides delete or replace the same anchored block incompatibly
- duplicate-block disambiguation becomes ambiguous after concurrent edits

Phase 1 does not need a full semantic merge implementation, but the storage model should preserve the data needed for it.

## Diff Contract

Diff results should be occurrence-based, not just path-based.

```v
pub enum MarkdownDiffOp {
	added
	removed
	moved
	edited
	reused
}

pub struct MarkdownDiffEntry {
pub:
	op              MarkdownDiffOp
	occurrence_id   string
	content_id      string
	kind            string
	old_anchor      string
	new_anchor      string
	old_order       int
	new_order       int
}
```

This gives much better UX than top-level index diffs when blocks move.

## Derived Indexes

Do not overload JSON-path indexes for Markdown.

Instead, add projector-backed derived indexes later:

- block kind index
- heading text index
- code language index
- outbound link host index

Possible internal row shapes:

```text
md_blocks(doc_root_id, occurrence_id, kind, anchor, content_id)
md_headings(doc_root_id, occurrence_id, level, text)
md_code_blocks(doc_root_id, occurrence_id, lang)
```

These can later power SQL or API surfaces without changing Markdown storage itself.

## Encoding Notes

`MarkdownRef` should have its own binary encoding and should not be encoded as JSON text.

Suggested layout:

```text
[version:u8]
[doc_root_len:u16][doc_root_id bytes]
[source_hash_len:u16][source_hash bytes]
[source_len:i64 sortable]
[ast_version:u8]
[parse_flags:u32]
```

Rules:

- deterministic
- explicit versioning
- no map iteration
- no text JSON wrapper

## Interaction With Existing Typed Codec

`TypedValueEncoder.validate`, `encode_value`, and `decode_value` will need a new `markdown_` branch.

Validation should check:

- payload is a `MarkdownRef`
- `doc_root_id` is non-empty
- version fields are in supported ranges

Because `ColumnValue` currently does not include a structured variant, the least disruptive path is:

- Phase 1: keep `markdown_` writes on dedicated helper APIs
- Phase 2: extend `ColumnValue` with `MarkdownRefValue`

That avoids forcing a union-type migration before the storage model is proven.

## Suggested Phase Plan

### Phase 1

- add `ColumnType.markdown_`
- define `MarkdownRef` encoding
- add explicit Markdown read/write helpers
- persist chunk/root/manifest side structures
- support read-back to original Markdown text or normalized render

### Phase 2

- add occurrence-aware diffs
- add block-level projections and indexes
- expose document/block inspection APIs

### Phase 3

- add Markdown-aware three-way merge
- add merge preview and conflict reporting at block granularity
- add move-aware heuristics for repeated blocks

## Open Questions

- whether source text should be preserved verbatim alongside AST chunks for exact round-trip formatting
- whether inline nodes need occurrence IDs in Phase 2 or only block nodes
- whether Markdown roots should live in repository virtual roots or database-local side storage
- whether user-facing SQL should expose Markdown columns as scalars, pseudo-tables, or both

## Recommendation

Implement the first version with:

- `ColumnType.markdown_`
- row-stored `MarkdownRef`
- side-stored document/chunk/manifest records
- `content_id + occurrence_id` dual identity
- explicit helper APIs for ingest and retrieval

That gives PollyDB a path to efficient agent-memory storage without forcing premature SQL or merge-surface complexity.
